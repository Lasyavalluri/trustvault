# TrustVault threat model and test evidence

## Scope and security boundary

This implementation is a local challenge/demo build. The application server, SQLite database, private file directory, and development HMAC key are on one host. The in-app audit chain detects modification when the attacker cannot also change the HMAC key and recompute the chain. It is not independently immutable against a host administrator, database administrator with the key, compromised application process, or an attacker able to rewrite the database and key together.

The current tree does not provide a public deployment, production identity provider, malware scanner, external WORM audit anchor, PostgreSQL migration, or scheduled byte purge. Do not use production confidential documents until those gaps and deployment controls are addressed and tested.

## Threats, controls, and tests

| Threat | Control in this build | Test evidence |
|---|---|---|
| Guess or substitute another user's document ID | Every document route queries the document and evaluates current owner/grant; unknown and unauthorized IDs share a 404 response. | `test_ungranted_user_cannot_read_download_or_search_other_users_document` |
| Directly request the download route without a UI link | Download route independently invokes current read authorization and streams only from private storage. | `test_ungranted_user_cannot_read_download_or_search_other_users_document`; `test_upload_validation_and_owner_only_access` |
| Remove a grant but reuse an old cookie or previously visited document | Grants are read from SQLite on each request; grant state is not embedded in the session. No signed download URL exists. | `test_revocation_blocks_the_next_read_and_download` |
| Search, category, owner, or date filter leaks another user's documents/counts | The SQL query scopes to owner or current grant before searching and filtering. | `test_ungranted_user_cannot_read_download_or_search_other_users_document` |
| A viewer posts an edit or delete directly | Edit checks owner/admin/edit grant; delete requires owner or administrator. UI visibility is not the policy. | `test_read_grant_cannot_edit_and_admin_can_manage_data_lake`; `test_edit_grant_allows_edit_but_not_permission_management_or_deletion` |
| A viewer replaces content by posting directly to the content endpoint | The replacement route independently requires owner/admin or active `edit` grant and validates the replacement file. | `test_named_editor_can_replace_content_and_every_change_is_audited`; read-only direct edit denial is covered by `test_read_grant_cannot_edit_and_admin_can_manage_data_lake`. |
| Administrator data-lake privileges are used to reach documents | Administrators can read, download, edit, delete, and manage grants across the data lake by design. All such routes still check the active admin session and record events. **Accepted authority:** compromise of an admin account has broad impact; production should use MFA/SSO, least-privilege admin separation, alerting, and approval for especially sensitive actions. | `test_read_grant_cannot_edit_and_admin_can_manage_data_lake` |
| Disabled account keeps using a cookie/session or a grant after reactivation | Middleware checks account activity per request; disablement deletes sessions and revokes every active grant, with per-grant audit events. Historical user and audit rows remain. | `test_disabled_account_loses_access_even_with_an_old_cookie` |
| A deleted document remains accessible through an old URL | Deleted records are excluded from all document queries before metadata or bytes are returned. | `test_owner_deletion_blocks_future_access_and_keeps_an_audit_record` |
| One demo viewer's credentials or grants are shared with other test viewers | Provision four distinct active viewer accounts with independent generated passwords; grants remain bound to each account ID. | Four-account provisioning test; per-account grant isolation is exercised by route-level authorization tests. |
| Cross-site form submits a grant or other mutation | Per-session CSRF token required on mutating form routes; SameSite=Lax is supplementary. | `test_csrf_is_required_for_grants_and_audit_modification_is_detected` |
| Filename traversal overwrites or reads an arbitrary path | Display filename is never used as a storage path; random server-generated keys are used in a private directory. | `test_traversal_filename_never_becomes_a_storage_path` |
| Spoofed type, active content, malformed Office archive, or oversized upload | Narrow allowlist, extension/type match, signature and Office ZIP checks, request cap, file cap, private storage, attachment disposition, `nosniff`. These checks do not replace malware scanning. | `test_upload_validation_and_owner_only_access`; oversize/malformed Office cases remain to add. |
| HTML stored-XSS through a document name or audit field | Jinja autoescaping is enabled; HTML/SVG uploads are rejected; downloads are attachments. | `test_template_escapes_document_names` |
| Audit records are silently edited through application routes | SQLite triggers reject normal audit row updates/deletes; HMAC chain is verified on the admin view. | `test_csrf_is_required_for_grants_and_audit_modification_is_detected` drops the trigger to simulate database tampering, then asserts verification fails. |
| Audit tail is removed or host/key is compromised | **Accepted for the local demo:** no independent signed checkpoint/WORM storage exists, so privileged host/key compromise or truncation of the final unanchored tail may evade detection. Add an external append-only anchor and alerting before production. | Current tests detect editing an event but do not simulate an independently anchored chain because no external anchor is implemented. |
| Existing downloaded bytes remain usable after revocation | **Accepted limitation:** the application blocks the next request, but cannot recall downloaded bytes or data already in flight. No persistent signed links are issued. | `test_revocation_blocks_the_next_read_and_download` checks subsequent requests. |
| Deleted document bytes remain recoverable from disk | **Accepted limitation:** deletion makes the record inaccessible immediately but retains bytes; no purge/recovery scheduler exists. | No purge test; implement byte purge and verify backup expiration before promising erasure. |
| Brute-force or account enumeration | Generic login failure, per-IP-and-account-derived bucket rate limit, dummy scrypt verification for unknown users, and scrypt password hashes. Production deployments still need edge rate limiting and monitoring. | `test_login_failures_are_generic_rate_limited_and_login_rotates_session` |
| Repeated or concurrent share requests produce confusing access/audit state | Active grant uniqueness and SQLite write transaction serialize changes; permission changes preserve a previous/new value in audit details. | Functional access tests exist; concurrency stress test remains to add. |
| A recommendation silently becomes a grant, or a stale recommendation is reused | Local assistant only suggests exact department/domain matches, always recommends `read`, persists a pending suggestion, and requires a matching explicit administrator approval. Rejects and approvals are audited. | `test_local_access_assistant_only_grants_after_admin_approval` |
| An ambiguous or manipulated chat command changes a grant without authorization | Admin-only deterministic parser accepts narrow exact command formats, resolves exact document/account matches, binds a short-lived confirmation token to the initiating administrator, rechecks current state, and makes no change until explicit CSRF-protected confirmation. Cancellation also leaves grants unchanged. | `test_admin_agent_chat_requires_confirmation_to_grant_and_revoke` |
| A chat action is replayed after permission revocation or token exposure | Confirmation token is random, stored only as a hash, actor-bound, five-minute expiry, consumed after success/cancel, and current grant/account state is rechecked before mutation. **Accepted interface limitation:** anyone with an active administrator's session and ability to perform CSRF-protected actions can administer grants; use MFA/SSO and session protections in production. | `test_admin_agent_chat_requires_confirmation_to_grant_and_revoke` |
| Incorrect department metadata causes over-broad recommendations | Department must exactly equal a configured document domain; title does not widen access; suggestions are one document at a time and require human review. Incorrect admin-maintained profiles remain a risk and should be reviewed operationally. | `test_local_access_assistant_only_grants_after_admin_approval`; profile editing is separately administrator-authorized. |
| An external model receives confidential file contents without informed choice | Gemini is optional, administrator-only, and preceded by an upload disclosure; no document is sent unless the administrator checks the option. The local access recommender does not call Gemini. **Accepted external-processing risk:** once sent, Google processing/retention is outside this app's control; only enable for data approved by organizational policy. | `test_gemini_domain_mismatch_requires_confirmation_before_storage` mocks the provider and verifies it does not grant access. No real confidential document is sent by tests. |
| Prompt injection or malformed Gemini output changes permissions or invents a domain | Document is treated as untrusted input; Gemini is asked not to follow its instructions or grant access. Structured output is length/type checked and domain suggestions are normalized to the configured list; malformed values fail closed. A model summary may still be inaccurate and needs human review. | `test_gemini_domain_mismatch_requires_confirmation_before_storage`; direct malformed-output cases remain to add. |
| Gemini domain mismatch is silently stored under the model's choice | The upload enters private pending storage for 15 minutes; only the initiating active administrator can confirm or cancel with CSRF and a hashed one-time token. No document row or grant exists before confirmation. | `test_gemini_domain_mismatch_requires_confirmation_before_storage` |
| Data leaks through static files, browser cache, errors, or permissive CORS | No static mount for document bytes; response `no-store`; generic errors; no separate frontend/CORS layer. | Route tests plus review of static mount and response middleware; production proxy cache must also be configured safely. |
| Session fixation | Successful login deletes the pre-auth session and creates a new random session identifier. | `test_login_failures_are_generic_rate_limited_and_login_rotates_session` |
| Upload request has no declared size and streams without a cap | Upload route rejects requests without Content-Length; size header and actual file read are capped. | Add a focused request-limit test before deployment. |

## Operational controls still needed

1. Deploy behind HTTPS, use secure cookies, configure trusted hosts/proxies and rate limits, and place audit key in a secrets manager separate from the database.
2. Use PostgreSQL or another supported managed database with migrations and tested backups; keep files in private object storage with lifecycle/retention controls.
3. Anchor periodic signed audit checkpoints outside the app/database trust boundary and alert on verification failure.
4. Add malware scanning or quarantine/review; maintain a documented allowlist and size limits.
5. Define and test retention, recovery, physical purge, and backup expiration; a soft delete is not secure erase.
6. Add tests for every remaining row marked “remains to add” before claiming the matching threat is covered.
7. Treat Gemini as a separately approved data processor: confirm contractual terms, region, retention, and training settings before enabling a production key.
